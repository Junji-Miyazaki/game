## CONFIRMED DEFECTS

### D1. OVERDRIVE が「逆転設計」ではなく「上級者の最適開幕」になっている（実測で支配戦略）

- **場所**: `js/games/meteor.js:88-90`（定数）、`:1018-1034`（エッジ判定）、`:1120` / `:1150`（スコア ×2）、`:543-547`（CT 半減）
- **何が壊れるか**: METEOR_MODERN_PLAN.md は OVERDRIVE を
  「負け際を見せ場に変える逆転設計」と定義している。しかし都市は復活せず、都市の数はミサイル同時上限
  (`_getMissileCap` は `_launcherSlots` のみ参照) にも火力にも一切影響しない。つまり
  **漏らさないプレイヤーにとって 4 個の予備都市は完全な死に資産**であり、それを捨てるだけで
  ラン全体にスコア ×2 と発射 CT 半減が恒久的に付く。コストはステージ 1 回分の BANISH のみ。
- **具体的な失敗シナリオ（実測）**: 同一 AI・同一フレーム予算 (120,000 フレーム ≒ 33 分) ・各 4 ラン。
  「地面に最も近い隕石を常に迎撃する」上級者相当ボットで比較:

  | 戦略 | 平均スコア | 生存 |
  |---|---|---|
  | 5 都市を守る（安全） | **621,618** | 4/4 生存・**全ラン 5 都市無傷** |
  | 開幕で 4 都市を捨てる | **963,118** (1.55×) | 3/4 が最後まで生存 |

  安全プレイ側が 4 ラン全部で都市を 1 個も失わなかった事実が核心 — その 4 個は使われないので、
  捨てるコストが実質ゼロ。**上級者ほど捨てるのが正解になる。**
  （補足: 下手なボット（ランダム狙い）では逆に sacrifice が大損 7,803 vs 1,694,302。
  つまりこの機構は「弱者を救済する」のではなく「強者だけを追加で優遇する」向きに効いている＝意図の反転。）
- **修正案**（いずれか）:
  1. ステージクリア時に **生存都市 1 個あたりの固定ボーナス**（例 `+150 × 生存都市数 × (stage+1)`）を
     加算し、都市を保持する価値を作る。sacrifice の +100% と釣り合う額にすれば選択制になる。
  2. `OVERDRIVE_SCORE_MULT` を廃し、CT 半減（＝救済として本質的な部分）だけ残す。
     見せ場の演出はビネットと OVERDRIVE 表示で既に足りている。
  3. スコア ×2 を「OVERDRIVE 中に稼いだ分」ではなく「OVERDRIVE 状態でステージをクリアした時の
     一括ボーナス」に変える（背水で耐え切った瞬間だけ報われる＝逆転設計に忠実）。

### D2. コンボ倍率が無制限で、通常プレイで 40〜80 倍に達する

- **場所**: `js/games/meteor.js:75`（`COMBO_SCORE_STEP = 0.10`）、`:1100`（`const comboMult = 1 + COMBO_SCORE_STEP * this.combo;`）
- **何が壊れるか**: 倍率に上限が無い。コンボは「撃破のたびに 2 秒ウィンドウをリセット」なので、
  隕石密度が上がる中盤以降は**ウィンドウが切れず一方的に伸び続ける**。
  設計コメントは「コンボ1につき+10%」とだけ書かれており、3 桁コンボを想定していない。
- **具体的な失敗シナリオ（実測）**: 上級者ボットの通常プレイで最大コンボ
  **554 / 447 / 393 / 438**（＝倍率 **56.4× / 45.7× / 40.3× / 44.8×**）。
  高速連打ボットでは **811**（＝**82.1×**）。ステージ 12〜13 到達時点でスコアは 50〜70 万に達し、
  その大半がコンボ倍率由来。結果として「何体倒したか」ではなく
  「何秒間チェーンを切らさなかったか」だけがスコアを決め、隕石サイズボーナス・COIN・
  ステージクリアボーナス（`:927` の `100 + stage*50`、倍率非適用）がすべて誤差になる。
  ボス撃破スコア (`BOSS_SCORE_BASE=250`) の設計意図も同時に無意味化する。
- **修正案**: 倍率を頭打ちにする。
  ```js
  const COMBO_MULT_CAP = 4;   // 例: 最大 4 倍（コンボ 30 で到達）
  const comboMult = Math.min(1 + COMBO_SCORE_STEP * this.combo, COMBO_MULT_CAP);
  ```
  コンボ表示 (`_drawComboHud`) は現在の生カウントを出し続けてよい（伸ばす快感は残る）。
  上限に達したら `xN` を別色にすると「MAX」の手応えが出る。
  なお REROLL 獲得閾値 (`REROLL_COMBO_THRESH=10`) はこの変更の影響を受けない。

## MINOR NOTES

- **M1. カード画面のフロートが暗転オーバーレイの下に描かれ、ほぼ見えない。**
  `render()` は `_drawFloaters` (`:1753`) → `_drawCardChoice` (`:1814`) の順で、後者が
  `globalAlpha 0.75` の黒で全面を塗る (`:1846-1848`)。よって `POOL LIMIT` (`:611`) と
  `BANISH +1` (`:952`) は実効 25% 不透明度でしか見えない。`:1201-1203` のコメントは
  「カード画面上のフロートは進行する」と明示しており、更新は確かに動いている（M5 の凍結テストで確認）が、
  **見せる部分が実装されていない**。修正: `_drawCardChoice` の末尾（`ctx.restore()` の直前）で
  もう一度 `_drawFloaters(ctx, p)` を呼ぶ。

- **M2. `MIN_DRAWABLE_POOL = 3` の不変条件は実際には守られていない（動作は安全）。**
  `_banishCard` (`:604-608`) は「`slots` が最大なら除外」を*その時点の* `_launcherSlots` で数える。
  `_launcherSlots = 4` の時点で「残り {slots, chain, shock} = 3」ちょうどまで BAN した後、
  プレイヤーが SLOTS+ を取って 5 にすると `slots` がプールから消え、`_pick3Upgrades()` が
  **2 枚しか返さない**。構築して実測済み: `AFTER slots maxed -> cards offered = 2 => shock,chain`。
  ただし 2 枚画面は正常動作する（空の 3 枠目タップは `_cardHitTest` が -1 を返して無反応、
  実カードのタップは正常にクローズ、さらなる BANISH は POOL LIMIT で正しく拒否、消費もされない）。
  ソフトロックもクラッシュも無いので実害は「稀に選択肢が 2 枚になる」だけ。
  厳密にするなら guard 側で `slots` を無条件に除外して数える（`_launcherSlots` の現在値を見ない）。

- **M3. カード画面上に BACK ボタンが描かれるが押しても何も起きない。**
  `engine.js:90` の `_drawBack()` は `scene.render()` の**後**に呼ばれるため、暗転オーバーレイの上に
  BACK が乗る。`blocksBack()` が true なので機能は正しく無効化されている（誤脱出防止は成功）が、
  押せそうな見た目で無反応なのは軽い UX 不整合。`_drawBack()` を
  `if (!(this.scene.blocksBack && this.scene.blocksBack())) this._drawBack();` にすれば消える。

- **M4. `meteor.js:974` の防御的 splice だけが `_bossIdx` を補正していない。**
  `if (!m || m.x == null) { this.meteors.splice(i, 1); continue; }` — ファイル内の他 3 箇所の splice
  (`:989`, `:1083`, `:1167`) はすべて `_bossIdx` を調整している。`m.x == null` は現状の生成経路では
  発生しないため到達不能だが、防御コードとして残すなら他と揃えるべき。

- **M5. ボス HP バーとアイテムパネル枠が重なる。**
  HP バー (`:2198-2201`) は x 52-352 / y 51-55、アイテムパネル枠 (`:2326`) は x 0-92 / y 52 起点。
  x 52-92 で重複。ボス戦中に SCATTER/RAPID/バフが乗っていると線が交差する。実害は見た目のみ。

- **M6. カード枠のフェードインが効いていない。**
  `_drawUpgradeCard` は `:1980` と `:1992` で `globalAlpha` に**絶対値 1** を代入するため、
  呼び出し側 (`:1852`) が設定した `fadeIn` を上書きする。開幕 0.25 秒、背景の暗転だけがフェードし
  カード枠は最初から全不透明で出る。`ctx.globalAlpha = alpha1` のようにフェード値を持ち回れば直る。

## EXPLOIT ANALYSIS

指示された 3 つの degenerate 戦略を個別に検証した。**2 件は本物、1 件は否定、追加で 1 件発見。**

### X1. 都市を意図的に捨てて OVERDRIVE を常時化 — **本物（D1 参照）**
上級者ボットで平均 1.55 倍、しかも 4 分の 3 が完走。詳細と修正案は D1 に記載。
なお「弱いプレイヤーには不利、強いプレイヤーには有利」という向きなので、
放置するとスコアランキングは「開幕自殺した上級者」で埋まる。

### X2. コンボによる無限倍率 — **本物（D2 参照）**
「無限」ではないが実効的に青天井。ステージ境界では必ず切れる（クリア条件が `meteors.length === 0` で、
次ステージ初弾は隕石速度 2-7px/s × 落差 638px ≒ 90-300 秒かかるため 2 秒ウィンドウは確実に途切れる）。
したがって**ステージ内**で 400-800 まで伸びるのが上限で、それでも 40-80 倍。
なおカード画面はコンボとそのウィンドウを凍結保存して次ステージへ持ち越すが、
上記の理由で持ち越し分は必ず失効するため、これ自体は exploit ではない。

### X3. REROLL / BANISH のファーミング — **否定（exploit ではない）**
- REROLL: `_comboRewarded` ラッチ (`:1105-1112`) が正しく機能し、コンボが 0 に戻るまで再付与されない。
  さらに `REROLL_CAP = 3` で保有上限。52 万フレームのソークで保有数が 3 を超えた瞬間は一度も無い。
- BANISH: `BANISH_CAP = 3` で保有上限。ラン累計の BAN 回数は無制限だが、
  `MIN_DRAWABLE_POOL` ガードが最大 7 回で打ち止めにする（実測: `bans accepted = 7`）。
- チェーンカスケードによる爆発の無限増殖も否定: CHAIN/SHOCK 有効な 52 万フレームで
  同時爆発数の最大は **133**、隕石は最大 185 で頭打ち。新規爆発は配列末尾に push され、
  降順ループ (`:1052`) では同フレーム再訪されないため自己再帰もしない。

### X4. 【追加発見】BANISH でレアリティ経済を破壊できる — **軽度だが本物**
BANISH に「COMMON しか消せない」等の制限が無い。COMMON 6 種を全部 BAN すると
抽選プールが RARE 4 種 (`slots/chain/shock/shield`) だけになり、以後**毎回必ず RARE が 3 枚**出る。
`COMMON:RARE = 3:1` の重み付け (`:561`) が完全に無意味化する。
さらに `slots` を 5 まで取り切るとプールが `{chain, shock, shield}` の 3 種ちょうどになり、
**カード画面が毎回まったく同じ固定 3 枚**になる（ランダム性ゼロ）。
コストは「都市無傷クリア 6 回」で、上級者には十分現実的（上記ボットは 12 ステージを無傷で走破）。
クラッシュはしない（sim で構築・確認済み）。
修正案: BANISH 済み ID を N ステージ後に復活させる、または RARE の BAN を禁止／別コスト化する。
最小の対処なら `MIN_DRAWABLE_POOL` を 5 程度に引き上げるだけでも固定化は防げる。

## 総括

P1〜P3 の実装品質は高く、**指示された危険項目に該当する実装バグは 1 件も見つからなかった**。
特にスコア計算の単一経路化（全キルが同じ `hp<=0` ブロックを通る）、`enter()` の網羅的リセット、
カード表示中の完全凍結、`_bossIdx` の全 splice 経路での付け替えは、いずれも実測で正しさを確認した。

一方で、**バランス定数が実プレイのスケールに追随していない**。
OVERDRIVE (D1) は設計意図と逆向きに作用し、COMBO (D2) は他のスコア源をすべて誤差に変える。
この 2 つは 1 行ずつの定数／式変更で直せるので、実機確認の前に手当てすることを推奨する。
M1（カード画面のフロートが見えない）も P3 のフィードバック設計が実際には届いていない点で、
同時に直す価値がある。
